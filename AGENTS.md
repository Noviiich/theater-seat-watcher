# Инструкции для работы над theater_tickets

@/home/novich/.codex/RTK.md

## Назначение

Python-бот для Telegram отслеживает новые сеансы Орловского театра «Свободное
пространство» в QuickTickets, выбирает заданное количество соседних мест,
оформляет удержание до оплаты и отправляет пользователю ссылку на оплату.
При появлении нескольких подходящих сеансов обрабатываем **каждый** в пределах
заданных пользователем лимитов. Оплату выполняет пользователь.
По уточнению пользователя оплата удержанного заказа доступна 20 минут: первый заказ оформляется
сразу, затем через 1200 секунд бот повторно выбирает места, оформляет новый
заказ и присылает новую ссылку. Цикл действует до остановки пользователем или
конца срока отслеживания; статус оплаты автоматически не запрашивается.

## Принципы реализации

- Базовый стек: Python 3.12+, asyncio, aiogram 3, httpx, SQLAlchemy 2,
  Alembic, SQLite для одного экземпляра. Точные версии фиксировать в `uv.lock`.
- Домен и алгоритм мест не зависят от Telegram, HTTP, ORM и Playwright.
  Внутренние URL и поля QuickTickets остаются внутри адаптера провайдера.
- Различать спектакль (`event`), конкретный сеанс (`session`) и HTTP-сессию.
  ID провайдера нормализовать в строки; ключ сеанса включает alias театра.
- Новизна определяется по сохранённому ID сеанса. Перенос даты, изменение цены,
  возвращение мест и повторное появление известного ID — другие события.
- Первый полный снимок создаёт baseline без массового бронирования старой афиши.
  Новые подписки также получают собственную точку отсчёта.
- Для количества больше одного обязательна одна непрерывная группа в одном
  ряду и сегменте без прохода. Не ослаблять соседство ради завершения заказа.
- Деньги — целые копейки, преобразование API через Decimal, никогда float.
  Время хранить в UTC, показывать в Europe/Moscow; не угадывать год по текущему.
- Каждый запрос на оформление сохранять до внешнего вызова. После таймаута
  изменяющего запроса сначала выяснять результат; не повторять его вслепую.
- Различать новый цикл бронирования и технический retry: один Candidate на
  покупателя/сеанс, последовательные RenewalCycle, не более одной активной или
  неопределённой брони на Candidate. Ключи идемпотентности и outbox включают
  cycle_no; рестарт не создаёт новый цикл.
- Интервал повторного оформления — 1200 секунд от начала удержания, а не от
  отправки сообщения. По продуктовой настройке после этого срока создаётся
  новый цикл без запроса статуса старой оплаты. Явная остановка, пауза или
  `watch_until` прекращают автоматический цикл.
- Старые циклы сохранять в истории и освобождать их локальный allocation через
  1200 секунд. Новый цикл не расходует ещё один слот сеанса в пакете. Отсутствие
  проверки оплаты означает, что бот продолжит повторы и после оплаты, пока
  пользователь явно не остановит Candidate.
- Проверять количество, соседство, итоговую стоимость и срок удержания по
  ответу провайдера. Выбор в интерфейсе ещё не подтверждает бронь.
- Уведомления отправлять через persistent outbox. Сбой Telegram не должен
  создавать новый заказ. Не обещать exactly-once для внешних сервисов.
- Лимиты применять атомарно: к сеансу, пакету обнаружения и активным заказам
  покупателя. Учитывать операции с неизвестным результатом и комиссии.
- Отсутствие цены, неизвестный статус места, несовпадение схемы, неполный
  ответ или неподтверждённая возможность оплаты должны давать явный результат,
  а не фиктивную успешную бронь.

## Работа с интеграциями

Подтверждённые чтением контракты и гипотезы перечислены в исследовании API.
TTL удержания 1200 секунд сообщён пользователем и подтверждён сохранённой
страницей оплаты QuickTickets как требование продукта.
Проверить его точку отсчёта и поля срока в checkout; фактический ответ провайдера
приоритетнее настройки. Не придумывать URL оформления, webhook или idempotency key.
После изменения контракта обновлять документ и обезличенные контрактные примеры.
Только публичный клиентский режим `scope=qt`, `panel=site`; не переключаться
на служебные режимы из общего JS-приложения.

Обычные проверки и CI работают с fake provider и сохранёнными обезличенными
ответами, без создания заказов. Реальное оформление включается явной настройкой
`BOOKING_MODE=live` после проверки контракта, профиля покупателя и лимитов.
Значение по умолчанию — `dry_run`; в нём не должно быть изменяющих запросов.
Не обходить CAPTCHA или ограничения доступа; возвращать `requires_user_action`.

Не сохранять в Git и логах `.env`, Telegram-токен, cookies, Authorization,
данные покупателя, приватные HAR и полные ссылки заказа/оплаты. Для диагностики
использовать внутренние идентификаторы. Telegram-команды доступны только
разрешённым user ID в личном чате; проверять также callback-запросы.

## Рабочий процесс

Все shell-команды запускать через `rtk`; для неподдерживаемых команд использовать
`rtk proxy <команда>`. Для поиска сначала `rtk rg` / `rtk proxy rg --files`.

Выполнять один логический шаг roadmap за раз. Каждый шаг должен быть пригоден
для самостоятельного коммита; сам commit создавать, когда это входит в задачу.
При изменении поведения синхронно обновлять документацию. Писать документацию
по-русски, идентификаторы и commit subjects — по-английски.

После появления инструментов проекта проверки: `rtk proxy uv run ruff check .`,
`rtk proxy uv run ruff format --check .`, `rtk proxy uv run mypy src`,
`rtk proxy uv run pytest`. Запускать проверки, относящиеся к изменению;
для изменения только Markdown достаточно проверить ссылки и согласованность.
Обязательны содержательные тесты соседства, дедупликации, лимитов, восстановления
после сбоя и неоднозначных ответов на оформление.
