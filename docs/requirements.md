# Требования и сценарии

## Цель и границы первой версии

Театр: [Орловский государственный театр «Свободное пространство»](https://quicktickets.ru/orel-teatr-svobodnoe-prostranstvo).
Alias: `orel-teatr-svobodnoe-prostranstvo`. Первая версия — личный бот одного
покупателя, один процесс приложения, несколько правил подписки.

Бот обнаруживает новый сеанс, проверяет фильтры, выбирает `N` соседних мест,
создаёт заказ с временным удержанием и присылает кнопку оплаты. Реквизиты карты
и подтверждение оплаты пользователь вводит на стороне продавца/платёжной системы.
Здесь «бронь» означает удержание в процессе покупки: доступность отдельной
операции QuickTickets `book` не предполагается.

**Выбор пользователя:** если одновременно появилось несколько подходящих
сеансов, бронировать на каждом в пределах заданного лимита. Каждый сеанс имеет
свой заказ, результат и ссылку; не объединять их в неподтверждённую общую корзину.

**Уточнение пользователя:** оплата удержанного заказа доступна **20 минут**. Первый заказ создаётся
сразу после обнаружения подходящего сеанса и мест. Затем для этого же сеанса
бот повторяет подбор и оформление через 1200 секунд и присылает
**новую страницу оплаты каждые 1200 секунд**, пока условия выполняются.
Это новая бронь с новой ссылкой, а не повторная отправка истёкшей ссылки.

## Подписка

| Настройка | Семантика |
| --- | --- |
| `event_ids` / `title_filter` | Конкретные спектакли или совпадение нормализованного названия; пусто — вся афиша театра |
| `date_from`, `date_to`, `weekdays`, `time_from`, `time_to` | Ограничения времени сеанса в Europe/Moscow; границы включительные |
| `ticket_count` | Положительное число мест **на каждый сеанс** |
| `seat_profile_id` | Проверенный профиль схемы, соседства и предпочтений |
| `max_ticket_price`, `max_order_total` | Предельная цена билета и полная сумма одного заказа с комиссиями |
| `max_sessions_per_batch` | Число сеансов, для которых разрешено начать оформление в одном пакете обнаружения |
| `max_batch_total` | Суммарный предел расходов на пакет, включая оплаченные в нём заказы |
| `max_active_orders`, `max_active_total` | Предел числа и суммы одновременно активных/неопределённых заказов покупателя |
| `priority` | Приоритет правила, если несколько подписок совпали с одним сеансом |
| `enabled`, `booking_mode` | Пауза; `dry_run` или `live` |
| `renewal_interval_seconds` | `1200`: интервал повторного оформления для отслеживаемого сеанса |
| `expected_hold_ttl_seconds` | `1200`: срок оплаты удержанного заказа; передан пользователем и отражён на платёжной странице |
| `watch_until` | Конец ожидания мест и повторных броней; по умолчанию начало сеанса, всегда не позже него |
| `availability_retry_seconds` | `180`: проверка мест, если подходящей группы пока нет; независимо от частоты чтения афиши |
| `max_cycles_per_session` | Необязательный предел циклов; по умолчанию без ограничения числа до `watch_until` |

Лимиты задаются заранее. До настройки количества, бюджетов и профиля покупателя
подписка может уведомлять и моделировать подбор, но не оформлять заказ.
Dry-run сохраняет отдельный результат подбора без intent, allocation и POST;
последующее включение live не оформляет старые симуляции задним числом.
Профиль покупателя для live checkout содержит фамилию, имя, отчество, email,
номер телефона и подтверждение согласия на обработку персональных данных.
Отсутствие любого обязательного значения прекращает оформление до внешнего POST;
значения хранятся вне Git и не попадают в логи или Telegram-сообщения.
Лимиты QuickTickets проверяются для каждого сеанса; запрос выше лимита нельзя
молча разбить на несколько заказов или переключить на коллективную продажу.
Льготы, Пушкинская карта, коллективные заказы и места без нумерации вне MVP.

## Новые сеансы и пакеты

1. Первая успешная полная загрузка создаёт baseline. Все уже опубликованные
   сеансы считаются известными; бот сообщает число найденных сеансов.
2. После baseline разность по `(provider, theatre_alias, session_id)` создаёт
   `SessionDiscovered`. Дата обнаружения не выдаётся за дату публикации сайта.
3. Все новые ID в одном полном снимке образуют сохраняемый `DiscoveryBatch`.
   Повтор обработки этого снимка после сбоя не создаёт второй пакет.
4. На каждом подходящем сеансе создаётся отдельная задача. Перед оформлением
   заново проверяются фильтры, доступность, профиль и лимиты. Задача хранит
   последовательность двадцатиминутных циклов для этого сеанса.
5. При отборе сеансов порядок: приоритет подписки, ближайшее время сеанса,
   затем ID. Превышение `max_sessions_per_batch` даёт `skipped_limit`;
   автоматически в следующий пакет такой сеанс не переносится. Его ручной
   повтор — отдельное явное действие. Временная нехватка денежного бюджета
   или активного лимита даёт `waiting_budget` до `watch_until`; при пробуждении
   проверяется также оставшееся число разрешённых сеансов в пакете.
6. Новый сеанс без открытой продажи или подходящей группы получает
   `waiting_availability` до `watch_until`. Повторное появление мест на старых
   сеансах из baseline не запускает покупки в MVP. У уже отслеживаемого Candidate
   ожидание мест продолжается и между повторными бронями. Его проверки и новые
   циклы не создают новый пакет и не сбрасывают лимиты.
7. Перенос/переименование известного сеанса обновляет данные и уведомляет при
   необходимости, но не создаёт новый Candidate или внеплановый цикл.
   Пропажа из одной афиши не доказывает отмену. Повторное появление известного
   ID не является новизной.

У каждой новой подписки собственный baseline. Его устанавливаем атомарно вместе
с обработкой полного снимка; уже известные к этому моменту сеансы не становятся
новыми из-за создания или редактирования правила. Пауза не сбрасывает baseline.
Просмотр старых сеансов и явный разовый запуск могут быть добавлены отдельно.

## Повторное бронирование каждые двадцать минут

1. На свободные подходящие места оформляется цикл № 1. Бот сразу отправляет
   состав, сумму, срок и ссылку, не дожидаясь общей границы двадцатиминутного таймера.
2. Следующая проверка привязана к началу удержания предыдущего заказа.
   Отправка сообщения не перезапускает TTL: задержка доставки уменьшает
   оставшееся время оплаты. Срок из ответа продавца имеет приоритет над 1200 секундами.
3. По истечении 1200 секунд бот не запрашивает статус предыдущего заказа и
   считает его цикл завершённым для планирования. Поэтому оплата не останавливает
   повторы автоматически: пользователь останавливает Candidate командой `/stop`.
4. После локального истечения 1200 секунд бот заново читает наличие и цены,
   ранжирует группы и создаёт цикл № 2 с новой ссылкой. Места могут измениться;
   сохраняются количество, соседство, порог удобства и бюджет. Операция повторяется
   для циклов № 3 и далее. Активную бронь досрочно не отменяем ради лучшей группы.
5. Если подходящей группы нет, бот ждёт и проверяет через 180 секунд до
   `watch_until`. Платёжное сообщение отправляется только при новой успешной
   брони; повторяющиеся сообщения «мест нет» каждый цикл не нужны.
6. Все подходящие сеансы ведут независимые циклы в пределах общих лимитов.
   Пропущенные интервалы после сбоя не компенсируются несколькими заказами:
   запускается максимум один новый цикл.
7. `/stop` для сеанса, пауза, подтверждённая отмена сеанса, истечение
   `watch_until` или заданного лимита циклов прекращают новые оформления.
   `/resume` возобновляет планирование от сохранённого состояния. Оплата не
   меняет цикл автоматически.

1200 секунд — продуктовый интервал нового цикла. Он не доказывает окончательное
истечение или неоплату старого заказа: пользователь сознательно выбрал повторы
без status-check. Задержка HTTP/Telegram или отсутствие свободной группы могут
сдвинуть новое сообщение.

Повторный цикл того же сеанса не расходует дополнительный `max_sessions_per_batch`.
Локальный allocation прошлого цикла освобождается через 1200 секунд, хотя
провайдерский исход не проверяется. На каждом цикле бюджет и ограничения
QuickTickets проверяются заново. Нехватка денег
или активного лимита у уже принятого Candidate даёт `waiting_budget` с проверкой
через 180 секунд; это не приём нового сеанса сверх лимита пакета.

## Telegram

Планируемые команды: `/start`, `/help`, `/subscriptions`, `/subscribe`,
`/pause`, `/resume`, `/stop`, `/settings`, `/preview`, `/orders`, `/status`.
Подписка создаётся мастером: фильтр → количество → профиль мест → бюджеты →
показ настроек → включение. `/preview` объясняет выбор группы без оформления.

При успехе сообщение содержит спектакль, дату, зал, ряд, номера мест, число
билетов, полную сумму, срок оплаты и кнопку «Оплатить». В пакетном итоге видны
успехи, отсутствие соседних мест, превышение лимита и ошибки по каждому сеансу.
Ссылку каждого успешного цикла отправляем отдельным новым сообщением сразу,
не ожидая завершения всего пакета. Указываем номер цикла и текущие места;
предыдущее сообщение по возможности отмечаем истёкшим и убираем его кнопку.
`/stop` и кнопка «Остановить повторы» действуют на конкретный сеанс; `/pause` —
на подписку. Начальный пакетный итог не ждёт конца всех повторных циклов.

Если есть только страница сеанса, кнопка называется «Открыть сеанс», а результат
не называется бронью. Если провайдер требует действия человека, сообщаем причину
и доступный следующий шаг. Нажатие «Оплатить» не доказывает оплату.

## Критерии результата

- При `N > 1` все места одной группы действительно соседние в проверенной схеме.
- Среди допустимых групп выбирается лучшая по воспроизводимому ранжированию.
- Два новых подходящих сеанса дают два заказа, если лимиты позволяют; иначе
  оформляется допустимое число с явным результатом для остальных.
- Перезапуск, повтор снимка, совпадение подписок и повтор Telegram callback
  не создают дубли внутри цикла или одновременно активные брони одного сеанса.
- Истёкший неоплаченный заказ автоматически сменяется новым примерно через
  двадцать минут при наличии подходящих мест; новый цикл получает свою ссылку.
- После `/stop`, паузы или окончания `watch_until` новые циклы не запускаются.
  Оплата не останавливает повторы автоматически; бюджет освобождается по
  локальному таймеру 1200 секунд.
- Потеря ответа на оформление блокирует повтор до выяснения результата.
- Сообщение с оплатой отправляется только для подтверждённого полного заказа;
  TTL и конечная сумма берутся из подтверждённого контракта провайдера.
- Сбой афиши/JSON не стирает baseline; сбой Telegram не теряет запись о заказе.
- Каталог, checkout и Telegram выполняются независимо: задержка одного направления
  не блокирует остальные. Второй процесс с той же SQLite-БД не запускает workers.
- `/status` показывает свежесть полной афиши, очередь outbox, неоднозначные
  оформления, ближайший цикл, состояние ожидания/остановки и оставшийся TTL,
  не раскрывая платёжные URL, токены или данные покупателя.
