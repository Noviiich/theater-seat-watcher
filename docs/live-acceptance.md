# Приёмка live-бронирования

## E2E всей текущей афиши

Тест `tests/e2e/test_live_current_catalogue.py` доступен только при явном запуске.
Обычный `pytest` его пропускает. Тест создаёт **новую отдельную SQLite-базу**,
записывает пустой baseline и затем считает все будущие сеансы текущей афиши
новыми. До изменяющих запросов он повторно читает сеансы, возможность обычной
продажи и свободные места. Для каждого сеанса, где алгоритм выбрал одно место в
пределах заданной цены, он запускает существующий live-checkout, проверяет один
подтверждённый заказ и отправленное Telegram-сообщение со ссылкой на оплату.
Оплату тест не выполняет. Изменение доступности между предварительной проверкой
и оформлением может привести к падению теста; это не разрешает повторять
неоднозначный изменяющий запрос.

Перед запуском нужны `BOOKING_MODE=live`, `TELEGRAM_BOT_TOKEN`,
`ADMIN_TELEGRAM_USER_ID` (получатель в личном чате с ботом),
`QUICKTICKETS_PAYMENT_TERMINAL_CHOICE`, полный профиль покупателя
`LIVE_E2E_LASTNAME`, `LIVE_E2E_FIRSTNAME`, `LIVE_E2E_MIDDLENAME`,
`LIVE_E2E_EMAIL`, `LIVE_E2E_PHONE`, а также положительные пределы
`LIVE_E2E_MAX_TICKET_PRICE_RUB` и `LIVE_E2E_MAX_ORDER_TOTAL_RUB`.
Последний должен быть не меньше первого; при неизвестной комиссии нужен запас.
Отдельная переменная `LIVE_E2E_DATABASE_URL` должна указывать на **ещё не
существующий** файл `sqlite+aiosqlite:///...` и отличаться от `DATABASE_URL`
рабочего бота. Созданную базу следует сохранить: в ней остаются намерения
checkout, заказы и outbox для разбора ошибок. Повторный запуск с этим же файлом
запрещён. Число активных заказов в тесте не ограничено: он действительно
пытается обработать каждый подходящий сеанс, а не только первый. Для тестовой
подписки установлен максимум один цикл на сеанс, поэтому двадцатиминутного
переоформления она не делает.

Перед чтением афиши тест проверяет, что бот видит личный чат получателя.
Получатель должен заранее открыть диалог с ботом и выполнить `/start`.

Для диагностического запуска на конкретном сеансе можно дополнительно задать
`LIVE_E2E_SESSION_IDS` как список ID через запятую. Без этой переменной тест
охватывает всю будущую афишу. Проверка одного сеанса не означает успешной
приёмки всех остальных.
Если нужно выбрать новое место после завершения предыдущего удержания,
`LIVE_E2E_EXCLUDE_SEAT_IDS` исключает перечисленные через запятую ID мест
из подбора в тесте. Это не снимает удержание у провайдера и не разрешает
создавать вторую активную бронь до окончания первого заказа.

После заполнения переменных окружения и осознанного подтверждения массового
создания реальных удержаний:

```sh
RUN_LIVE_E2E=1 LIVE_E2E_CONFIRM_ALL_SESSIONS=YES \
  rtk proxy uv run pytest -q tests/e2e/test_live_current_catalogue.py
```

Не запускать этот тест в CI или на рабочей базе. Успешный локальный прогон не
заменяет ограниченную live-приёмку контракта QuickTickets: если провайдер не
возвращает подтверждённый срок удержания, сумму или переносимую ссылку,
адаптер правильно остановит оформление и тест завершится ошибкой.

### Результат live E2E 26.09.2026

Запуск на отдельной новой SQLite-базе завершился `2 passed` за 122,51 с.
Афиша содержала 26 будущих сеансов. Предварительный отбор признал доступным
один (`s3159`); для него сохранён один заказ в состоянии `awaiting_payment`
с непустой платёжной ссылкой, а outbox подтвердил отправку одного сообщения
`payment` в Telegram. Остальные 25 кандидатов остались в
`waiting_availability`; тест не создавал для них заказов. В частности, у
шести сеансов с входными местами свежая карта `anyticket/anyticket` помечала
все 70 мест статусом `sell`, несмотря на базовое `free` в схеме зала.
Повторять тест на том же файле базы нельзя; новая попытка не нужна только ради
получения дополнительных ссылок на занятые места. Этот прогон подтверждает
путь от новой записи в афише до ссылки для одного реально доступного сеанса,
но не подтверждает live-оформление входного места или регулярное обнаружение
сеанса работающим production-процессом.

### Диагностика 26.09.2026

Read-only проверка нашла 27 будущих сеансов. Для 21 сеанса с нумерованными
креслами свободные места оставались только на `s3159` (47 на момент чтения).
Ещё шесть сеансов содержали только «входные места» без ряда и номера. Позднее
чтение публичного JS показало: эти элементы находятся в `response.places`,
а выбранные элементы типа `place` клиент отправляет через `hallplaces`.
Одиночное место теперь допускается к checkout, но фактическое оформление
такого места пока не проверено live; для нескольких билетов требование
соседних кресел сохраняется.

Первые две попытки E2E остановились до изменяющих запросов при разборе
ограничений продажи и входных мест. Для `s3159` сделана одна live-попытка:
её локальный checkout intent имеет неопределённый результат
`contract_changed`, подтверждённого заказа и платёжной ссылки нет. Позднейшее
чтение показало выбранное кресло свободным, но это не доказательство отсутствия
временного удержания. Повторять изменяющий запрос без выяснения результата
нельзя. Проверка `getMe` успешна, однако `getChat` для указанного получателя
вернула ошибку; тест дополнен ранним preflight Telegram до любого checkout.
Live-приёмка остаётся незавершённой.

Повторная проверка `getChat` позднее 26.09.2026 прошла: личный чат теперь
доступен. Локальный Chromium при разрешённом запуске открывает публичную
страницу сеанса с HTTP 200, поэтому отсутствие браузера или доступа к странице
не подтверждается как причина неопределённого checkout. Точный этап первой
попытки неизвестен: тогда сохранялось только последнее состояние intent.
В E2E добавлен вывод безопасных названий этапов checkout для следующей
диагностической попытки; новый изменяющий запрос до выяснения результата
первого не выполнялся.

После двадцатиминутного интервала проведена новая попытка для `s3159`.
Telegram-чат был доступен, сводное сообщение доставлено, но checkout снова
остановился до `hold_created`: записаны этапы `write_started`,
`response_received`, `ambiguous` с кодом `contract_changed`. Заказа и
платёжного уведомления нет; выбранное место позднее читалось как свободное.
Повторный POST в том же цикле не выполнялся. Read-only сравнение с `jQuery.param`
выявило несовпадение сериализации списка мест; код исправлен, но live-результат
после исправления пока не проверен. Проверку можно продолжить новым циклом
только после разрешения неопределённого результата или истечения ожидаемого
20-минутного удержания.

Досрочный диагностический запуск после явного запроса пользователя прошёл
провайдерский checkout для `s3159`: этапы `hold_created`,
`contact_form_received`, `confirm_started` и `validated` подтверждены.
Сохранение заказа затем не состоялось из-за локальной проверки, требовавшей
равенства итоговой суммы цене билета без комиссии. Ссылка не попала в базу и
Telegram; повторять checkout текущего цикла нельзя. Адаптер записи исправлен:
итог с комиссией принимается только в пределах заранее сохранённой цены билета
и максимальной суммы заказа; добавлен интеграционный тест. Публичная карта
показала для выбранного места `long_lock`, то есть удержание активно. Фактический
платёжный URL из завершённого браузерного контекста восстановить нельзя.
Следующий live-цикл возможен только после завершения текущего удержания или
подтверждённого освобождения места; успех исправления на реальном заказе ещё
не проверен.

## Контролируемый запуск 24.09.2026

Startup gate снят для конфигурации, где заданы `QUICKTICKETS_PAYMENT_TERMINAL_CHOICE`,
индивидуальные лимиты цены билета и суммы заказа. Для первой проверки
выбраны потолки 10 000 ₽ за билет и 50 000 ₽ за заказ. Запуск контейнера сам по
себе не создаёт live-подписок и не оформляет билеты: существующие dry-run
подписки остаются dry-run. Допущенный пользователь должен заполнить профиль покупателя,
выбрать число мест через «Новая подписка», ввести оба лимита и отдельно подтвердить
реальное оформление.

Live-подписка создаёт новую бронь и ссылку примерно через 1200 секунд от
начала предыдущего удержания для каждого принятого сеанса, пока пользователь
не остановит сеанс, не приостановит или не удалит подписку либо не наступит
начало сеанса. Автоматической проверки оплаты нет.

Telegram применяет число билетов и пределы цены/заказа отдельно к каждому
новому сеансу: несколько одновременно найденных сеансов могут создать несколько
заказов, а общая сумма может превысить лимит одного заказа. Эти условия видны
в подтверждении подписки. Миграция `0014` снимает прежние общие пределы
у live-подписок с настройками старого Telegram-мастера и возвращает пропущенные
по лимиту пакета сеансы в очередь, если срок их отслеживания ещё не истёк.
При расчёте перед финальным POST
проверяются стоимость билетов, комиссия и полный итог; сумма выше лимита
останавливает оформление. Неопределённый результат удержания/подтверждения
остаётся на ручной разбор без слепого повтора.

Этот запуск **не равен успешной live-приёмке**: реальный заказ и получение
платёжной ссылки ещё нужно проверить. Провайдерский ответ пока не даёт
доказательного `held_at`/`expires_at` и точных seat IDs в подтверждении;
длительность 1200 секунд используется как продуктовая оценка от момента
получения ответа на удержание. Проверить эти сведения вручную при первом заказе.
Не оставлять пробную подписку без присмотра; остановка доступна в «Мои
подписки».

## Preflight 21.09.2026

Это протокол подготовки шага 20, **не протокол успешной live-приёмки**.
Изменяющие запросы QuickTickets, удержание, отправка платёжной ссылки и оплата
в этой проверке не выполнялись.

| Проверка | Результат |
| --- | --- |

| Checkout transport | Production использует только dry-run и отключённый write transport |
| Финальный контракт | Ответ `/ordering/confirm`, полный состав и сумма заказа, срок и handoff оплаты не подтверждены |
| Reconciliation | Публичный lookup результата неоднозначного write не подтверждён; автоматический retry запрещён |

Дополнительное ручное наблюдение 23.09.2026 на `s3159` подтвердило цепочку
маршрутов до `POST /ordering/confirm` и последующего открытия страницы оплаты.
Содержимое запросов и ответов не сохранялось, поэтому состав полей, сумма, TTL,
ID заказа и переносимость ссылки остаются неподтверждёнными.

Веб-представление афиши доступно по [публичной странице театра](https://quicktickets.ru/orel-teatr-svobodnoe-prostranstvo),
но не заменяет свежие ответы API и проверку заказа. Предыдущие контролируемые
попытки и неизвестные исходы описаны в [исследовании API](quicktickets-api.md).
Вновь создать `short_lock` только ради проверки доступности нельзя.

## Условия допуска к одному контролируемому hold

1. Получить разрешённую сетевую трассировку обычного пользовательского checkout
   в стабильном браузере и установить фактический маршрут после contact form,
   состав отправленных полей, момент создания заказа и платёжный handoff. Из
   артефактов извлекать только обезличенные структуры; cookies, контакты,
   `orderCode` и URL оплаты не помещать в Git или логи.
2. Подтвердить на ответе провайдера точные seat IDs, полную сумму с комиссией,
   `held_at`/срок удержания или проверяемый остаток TTL, order ID и переносимый
   HTTPS URL. Если необходимый пункт недоступен, фиксировать ограничение, а не
   заполнять его догадкой.
3. Подготовить и вручную проверить YAML-профиль фактического зала: fingerprint,
   порядок мест, проходы, сегменты, предпочтения. Проверить полную валидацию
   приватного buyer profile без вывода значений.
4. Реализовать только подтверждённый публичный checkout transport и тесты его
   обезличенного контракта. После неоднозначного POST не повторять запрос до
   доказанного отсутствия удержания; если lookup не найден, оставить
   `needs_attention` и не открывать постоянный live-режим.
5. До изменяющего вызова сохранить intent и жёсткие лимиты: один Candidate,
   один сеанс, минимально нужное количество соседних мест, потолок полной суммы,
   один первый hold и не более одного нового цикла через 1200 секунд.

## Что записать во время приёмки

- Время обнаружения и доставки, измеренная задержка, внутренние ID и номер
  цикла — без приватных provider identifiers и URL в протоколе.
- Подтверждение состава соседних мест, общей суммы и срока из ответа провайдера.
- Открытие платёжной страницы в чистом браузерном контексте другого устройства;
  оплату выполняет пользователь, бот не вызывает `check_payment`.
- Переход от первого `held_at + 1200s` к одной новой брони и новой ссылке, затем
  `/stop` и отсутствие следующего checkout. Не оставлять тестовый цикл работать
  без присмотра.
- Проверку outbox/dedup, allocation и истории двух циклов после остановки и
  рестарта. При timeout или неполном ответе — сохранённый `needs_attention`,
  без слепого повтора POST.

На 21.09.2026 эти live-критерии **не были выполнены**. Это исторический
preflight; текущий ограниченный запуск описан выше и также не является
протоколом успешной приёмки.

## Ручная браузерная диагностика

Для первого пункта можно использовать отдельный инструмент наблюдения. Он
открывает страницу сеанса в видимом Chromium, но не выбирает места, не вводит
данные и не отправляет checkout. Все действия в окне браузера выполняет
оператор; нажатие кнопки на сайте может создать реальное удержание.

Сначала один раз установить Chromium для диагностической группы зависимостей:

```bash
uv run playwright install chromium
```

Затем запустить наблюдение, указав конкретный сеанс и новый путь отчёта:

```bash
uv run python scripts/observe_quicktickets_checkout.py \
  --session-url https://quicktickets.ru/orel-teatr-svobodnoe-prostranstvo/s1234 \
  --report /tmp/checkout-observation-20260923.json \
  --allow-manual-checkout
```

После закрытия вкладки отчёт содержит только метод, URL без query-параметров и
HTTP-статус ответов QuickTickets. В нём намеренно нет cookies, заголовков, тел
запросов/ответов, контактных данных, кодов заказа или ссылок оплаты. Отчёт не
заменяет ручную проверку итоговой суммы, TTL и переносимости оплаты.

Для контролируемого уточнения контракта добавьте `--capture-schema`. В этом
режиме отчёт дополнительно содержит только названия безопасных полей POST и
дерево названий полей/типов JSON-ответа. Значения, query-параметры, тела, коды
заказов и ссылки оплаты по-прежнему не записываются:

```bash
uv run python scripts/observe_quicktickets_checkout.py \
  --session-url https://quicktickets.ru/orel-teatr-svobodnoe-prostranstvo/s1234 \
  --report /tmp/checkout-schema-20260923.json \
  --allow-manual-checkout --capture-schema
```
