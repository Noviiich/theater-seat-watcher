# Исследование QuickTickets

Проверено 16.09.2026: прямые HTTP GET публичной афиши, страницы `/s3159`,
iframe, его JS и трёх JSON endpoints. Все перечисленные ниже проверенные GET
вернули HTTP 200. POST оформления, создание брони и оплата не выполнялись.
Публичная документация интеграционного API и webhook новых сеансов в изученных
материалах не найдены. Это не доказательство их отсутствия у провайдера.

Дополнение к требованиям: **пользователь сообщил, что бронь действует 3 минуты**.
Принимаем `expected_hold_ttl_seconds=180` и целевой интервал повторного оформления
180 секунд. Это сведения пользователя, а не результат выполненных GET. В checkout
нужно установить начало удержания и поле фактического `expires_at`, а также
подтверждение окончательного истечения неоплаченного заказа перед новым циклом.

## Афиша и инициализация

Афиша содержит карточки `data-elem-type="event"`, `data-filter-name`, ссылки
`/{alias}/e{event_id}`, `/{alias}/s{session_id}`. Внутри карточек найдены
`.event-filter-session` с `data-session-id` и `data-date` в формате `YYYY-MM-DD`.
Видимые и скрытые ссылки нужно дедуплицировать; скрытые дальние даты тоже читать.

На странице сеанса есть JSON-LD `startDate` с годом и смещением часового пояса.
Для s3159 проверено `2026-10-24T16:00:00+03:00`. Локализованное API-поле `dt`
само по себе не содержит год. При конфликте источников отклонять снимок сеанса
и сохранять диагностику, а не угадывать дату.

Iframe работает с `scope=qt`, `panel=site`, `user_id=0` и alias театра.
После сообщения `app_ready` родитель посылает `set_token` и `set_params`
с `elem={type: "session", id: 3159}`. В JS этот token используется как
`Authorization: Basic <token>`; дополнительно отправляются `Api-Id: quick-tickets`
и `Cache-Control: no-cache`. Это контекст публичной страницы, а не постоянный
API-ключ. TTL, связь с cookies/IP и правила обновления не установлены.

В исследовании GET JSON работали с токеном текущей страницы, заголовками выше,
`Origin: https://hall.quicktickets.ru` и соответствующим Referer. Передача cookies
для этих трёх запросов не потребовалась; из этого нельзя заключать, что checkout
также работает без cookie jar. Значения токенов в документацию не включаются.

## Подтверждённые запросы чтения

Base URL: `https://api.quicktickets.ru/v1/`.

Общие query-параметры проверенных вызовов:

```text
scope=qt
panel=site
user_id=0
organisation_alias=orel-teatr-svobodnoe-prostranstvo
elem_type=session
elem_id=3159
```

| Метод и путь | Проверенный ответ и назначение |
| --- | --- |
| `GET hall/hall` | `response.places`, `response.entranceplaces`, `response.background`: схема, координаты, базовые статусы и цены |
| `GET anyticket/anyticket` | `response.places`: отдельная карта текущей занятости по ID места |
| `GET anysession/anysession` | `response.events[].sessions[]`, `sell`, `book`, `collectiveSell` и ограничения продажи |

Дополнительно в JS найден `GET organisation/organisation`, но он не вызывался.
Endpoints служебных режимов общего приложения не входят в контракт бота.
`anysession/anysession` с конкретным `elem_id` не считать полным каталогом театра.

Урезанный пример одного реального места из `hall/hall`:

```json
{
  "id": 5054,
  "block": "Партер",
  "series": "1",
  "place": "13",
  "status": "free",
  "x": 180,
  "y": 90,
  "width": 24,
  "height": 24,
  "rotate": 0,
  "price": 700,
  "price_original": 700
}
```

Следующее место 5055 имеет номер `12` и `x=210`: нумерация в этом участке
идёт против увеличения координаты X. ID, номер и физический порядок различаются.
Цены отображаются сайтом в рублях; внутри бота переводить в копейки через Decimal.
`series` → метка ряда, `place` → метка места, `block` → название сектора;
эти метки не превращать в универсальные числовые индексы.

Для s3159 ответ схемы содержал 362 места с базовым `free`, а отдельный ответ
занятости — 288 записей `sell`, например `"5289": {"status": "sell"}`.
**Нельзя выбирать места только по `hall/hall.status`.** JS накладывает карту
занятости на схему; отсутствие записи в успешно полученной полной карте снимает
занятость, сохраняя `disabled` для отключённых мест. При ошибке/неполном ответе
отсутствие записи не означает свободное место. Новые неизвестные статусы считаем
недоступными. Эти два чтения не образуют атомарного снимка: перед заказом нужна
повторная проверка и обработка конфликта на стороне продавца.

## Ограничения, наблюдённые на s3159

`event_id=386`, `hall_id=16`; ID в данных встречаются и числами, и строками.

| Поле | Значение при исследовании | Последствие |
| --- | --- | --- |
| `sell.available` / `sell.max` | `true` / `4` | Обычная покупка до 4 мест на этом сеансе |
| `book.available` / `book.max` | `false` / `0` | Отдельная операция бронирования здесь отключена |
| `collectiveSell.available`, `min`, `max` | `true`, `2`, `5` | Другой сценарий, не использовать как автоматический обход `sell.max` |

Это снимок одного сеанса, не постоянные лимиты театра. Проверять их при каждом
оформлении. Временное удержание в процессе `sell` и отдельное действие `book`
имеют разную семантику; отключённый `book` не доказывает отсутствие удержания
при покупке, но и не подтверждает его.

## Начало оформления: подтверждено только чтением кода

1. Приложение зала отправляет родителю `action` и `selectedItemsInfo`.
   Для обычного сеанса структура выбора:

   ```text
   sessionAnyplaces:
     hallplaces: [provider_place_id, ...]
     entranceplaces: {}
     count: N
     amount: сумма в единицах сайта
   ```

2. Страница выполняет jQuery `POST https://quicktickets.ru/ordering/initAnytickets`.
   К структуре выбора добавляются `organisationAlias`, `elemType=session`,
   `elemId`, `collectiveSell=0`. В коде используется сериализация формы jQuery,
   не JSON; точное кодирование вложенных массивов закрепить сетевой записью.
3. При `res.result == "success"` страница читает `res.data.anyticketsCodes`
   и `res.data.selectAnyplacesCount`. Форма отправляет
   `POST https://quicktickets.ru/ordering/anytickets` с этими данными,
   `organisationAlias`, `elemType`, `elemId`; codes соединяются запятой.
4. Последующие поля покупателя, итоговые POST, редиректы и URL оплаты ещё не
   исследованы. Эти два пути не называем API подтверждённой брони или оплаты.

## Что обязательно выяснить до включения live

- Где именно возникают заказ и удержание, его ID и подтверждённый состав;
  как отсчитываются сообщённые пользователем 180 секунд, есть ли `held_at`,
  `expires_at` или остаток TTL и чем фактический срок может отличаться.
- Обязательные данные покупателя, авторизация, cookies, CSRF и условия форм.
- Полная сумма с комиссиями; возможен ли отказ от неподходящей суммы до удержания.
- Атомарность заказа на N мест, ответы на занятое место и частичное оформление.
- Как восстановить заказ после таймаута; есть ли поиск своего заказа, статус,
  отмена и поддерживаемый механизм идемпотентности. Не придумывать endpoints.
- Как получить URL оплаты/заказа, открываемый из Telegram на другом устройстве
  без cookie jar бота; проверить в чистом браузерном контексте.
- Как отличить paid, expired и cancelled. Истечение локального таймера само по
  себе не является подтверждением ни оплаты, ни отмены заказа.
- Различать истечение удержания и окончательное закрытие заказа для оплаты:
  может ли платёж по старой ссылке завершиться после освобождения мест, есть ли
  статус processing. До разрешения этого состояния повторную бронь не создавать.
- Можно ли после подтверждённого неоплаченного истечения оформить те же или
  другие подходящие места новым заказом; как быстро кресла освобождаются,
  какие ограничения частоты/повторных заказов применяются в этом сценарии.

Исследовательский шаг: записать минимальный сценарий оформления в браузере
с сетевой трассировкой до оплаты, очистить секреты из примеров, затем проверить
восстановление и переносимость URL. Повтор HTTP-сценария допускается только
после понимания последствий каждого запроса. При необходимости использовать
Playwright в отдельном адаптере; он сам по себе не решает переносимость ссылки.

Если удержание или переносимая ссылка недоступны, зафиксировать ограничение и
временно выдавать уведомление/подбор со ссылкой сеанса. Такой режим полезен,
но **не завершает** требование автоматического оформления; оно остаётся открытым.
