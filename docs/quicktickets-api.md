## Афиша и инициализация

Афиша содержит карточки `data-elem-type="event"`, `data-filter-name`, ссылки
`/{alias}/e{event_id}`, `/{alias}/s{session_id}`. Внутри карточек найдены
`.event-filter-session` с `data-session-id` и `data-date` в формате `YYYY-MM-DD`.
Видимые и скрытые ссылки нужно дедуплицировать; скрытые дальние даты тоже читать.
В публичных ссылках на сеансы после `/s` наблюдается числовой ID. При разборе
ссылок нельзя принимать `/subscription` и `/security` за сеансы: на афише
26.09.2026 это создавало два ложных ID и срывало весь снимок из-за отсутствия
названия спектакля.

На странице сеанса есть JSON-LD `startDate` с годом и смещением часового пояса.
Поле может находиться внутри `@graph` у объекта `@type=Event`; такая форма
наблюдалась 26.09.2026 на странице `s3132`.
Для s3159 проверено `2026-10-24T16:00:00+03:00`. Локализованное API-поле `dt`
само по себе не содержит год. При конфликте источников отклонять снимок сеанса
и сохранять диагностику, а не угадывать дату.

Iframe работает с `scope=qt`, `panel=site`, `user_id=0` и alias театра.
После сообщения `app_ready` родитель посылает `set_token` и `set_params`
с `elem={type: "session", id: 3159}`. В JS этот token используется как
`Authorization: Basic <token>`; дополнительно отправляются `Api-Id: quick-tickets`
и `Cache-Control: no-cache`. Это контекст публичной страницы, а не постоянный
API-ключ. TTL, связь с cookies/IP и правила обновления не установлены.

В исследовании GET JSON работали с токеном текущей страницы, заголовками выше,
`Origin: https://hall.quicktickets.ru` и соответствующим Referer. Передача cookies
для этих трёх запросов не потребовалась; из этого нельзя заключать, что checkout
также работает без cookie jar. Значения токенов в документацию не включаются.

В шаге 05 реализован только read-only `httpx`-клиент. Он получает cookie jar
внутри экземпляра, извлекает новый token из страницы сеанса и ограничивает
повторы GET. Изменяющие POST оформления остаются отдельным адаптером шага 13.

Повторная read-only проверка 18.09.2026 показала, что текущий ответ
`hall/hall` для `s3159` содержит только `background`, `entranceplaces` и
`places`: верхнеуровневый `hall_id` отсутствует. Это не повод выводить ID зала
из координат или мест. Адаптер принимает уже проверенный `hall_id` из деталей
конкретного сеанса и отклоняет ответ при конфликте двух источников. Без ID в
деталях сеанса inventory остаётся неполным.

В этом же ответе `places` теперь является объектом с ключом provider ID, а не
списком. Нормализатор принимает такую форму лишь при точном совпадении ключа с
полем `id` каждого места; иная форма или несовпадение остаются ошибкой
контракта.

Контролируемая browser-проверка 18.09.2026 повторила первый checkout на одном
свободном месте без оплаты. `POST /ordering/initAnytickets` вернул HTTP 200,
JSON `result=success` и объект `data` только с `anyticketsCodes` и
`selectAnyplacesCount`. После браузерной отправки второго шага отображается
форма контактов: `email` (required), `lastname` (required), `phone`, скрытые
`paymentTerminalSystem`, `paymentTerminalType`, `organisationAlias`,
`sessionId`, `anyticketsCodes`, `orderCode` и checkbox `personalDataConsent`.
Значения этих полей, cookies и коды заказа не сохранялись. Submit формы не
выполнялся: конечный маршрут, подтверждённая полная сумма, срок и переносимая
payment URL остаются неустановленными. Несмотря на текущие атрибуты required,
live-режим сохраняет продуктовое требование полного профиля покупателя и не
угадывает отсутствующие имена полей.

Ручное наблюдение 23.09.2026 на публичной странице `s3159` дошло до формы
оплаты. Зафиксированы ответы HTTP 200 на `POST /ordering/initAnytickets`,
`/ordering/anytickets`, `/ordering/loadExemptions`, `/ordering/calcAnytickets`,
`/ordering/checkEmailAndPhone` и `/ordering/confirm`; после `confirm` браузер
открыл страницу оплаты. Наблюдатель намеренно сохранил только методы, пути и
статусы: тела, поля форм, cookies, суммы, ID заказа и URL оплаты не записывались.
Это подтверждает последовательность маршрутов, но **не** подтверждает контракт
полей, результат удержания, TTL, итоговую сумму или переносимость оплаты.

Полная приватная HAR-трассировка 23.09.2026 подтвердила форму выбора мест
`sessionAnyplaces[hallplaces][]`, количество и сумму, успешный
`initAnytickets`, передачу `anyticketsCodes` и `selectAnyplacesCount`, расчёт
`amount`/`commission`/`total`, проверку контактов и финальный `confirm`.
`confirm` вернул JSON `result` и `data.url`; URL совпал с последующим открытием
HTTPS-страницы `/payment/order/<opaque-token>`. Форма ФИО использует одно поле
`lastname` с примером полного ФИО, поэтому адаптер передаёт в него фамилию, имя
и отчество через пробел. Значения ПДн, кодов и URL в Git не сохраняются.

## Подтверждённые запросы чтения

Base URL: `https://api.quicktickets.ru/v1/`.

Общие query-параметры проверенных вызовов:

```text
scope=qt
panel=site
user_id=0
organisation_alias=orel-teatr-svobodnoe-prostranstvo
elem_type=session
elem_id=3159
```

| Метод и путь | Проверенный ответ и назначение |
| --- | --- |
| `GET hall/hall` | `response.places`, `response.entranceplaces`, `response.background`: схема, координаты, базовые статусы и цены |
| `GET anyticket/anyticket` | `response.places`: отдельная карта текущей занятости по ID места |
| `GET anysession/anysession` | `response.events[].sessions[]`, `sell`, `book`, `collectiveSell` и ограничения продажи |

При live read-only проверке 26.09.2026 `sell`, `book` и `collectiveSell`
наблюдались непосредственно в `response`, а не внутри объекта сеанса.
Адаптер допускает обе полные формы, но отклоняет смешанные или частичные поля;
перед использованием ограничений всё равно проверяет наличие запрошенного ID
сеанса в `response.events[].sessions[]`. Область действия корневых полей
предполагается равной запросу с конкретным `elem_id`; это нужно подтвердить
при дальнейшей live-приёмке.

Та же афиша содержит шесть сеансов с 70 «входными местами» каждый:
в `hall/hall.response.places` у них `block="Входное место"`, а `series` и
`place` пусты. Это не нумерованные кресла; каждый элемент имеет собственный ID.
В публичном JS QuickTickets выбранные элементы типа `place` передаются через
`sessionAnyplaces[hallplaces][]`, а элементы типа `entranceplace` — через
`sessionAnyplaces[entranceplaces]`. Для этих шести сеансов
`hall/hall.response.entranceplaces` пуст. Поэтому одиночное свободное
ненумерованное место из `response.places` адаптер передаёт как `hallplaces`,
без вымышленных ряда и номера. Это подтверждено чтением контракта клиента,
но реальное оформление такого места ещё не проверено; отказ или неоднозначный
ответ checkout не считать успешной бронью. Несколько ненумерованных мест не
считать соседними креслами.

При повторном чтении 26.09.2026 все 70 мест каждого из этих шести сеансов
получили статус `sell` в свежем `anyticket/anyticket`. Базовое `free` из
`hall/hall` не означает доступности: при выборе обязательно применяется
актуальная карта занятости. Поэтому эти сеансы не были допущены к checkout.

При live-проверке `s3159` 26.09.2026 после успешного `confirm` выбранное место
читалось в `anyticket/anyticket` со статусом `long_lock`. Адаптер трактует
`long_lock` как удержание, а не как свободное место. Этот статус сам по себе
не раскрывает ссылку оплаты и не является проверкой оплаты.

Дополнительно в JS найден `GET organisation/organisation`, но он не вызывался.
Endpoints служебных режимов общего приложения не входят в контракт бота.
`anysession/anysession` с конкретным `elem_id` не считать полным каталогом театра.

Урезанный пример одного реального места из `hall/hall`:

```json
{
  "id": 5054,
  "block": "Партер",
  "series": "1",
  "place": "13",
  "status": "free",
  "x": 180,
  "y": 90,
  "width": 24,
  "height": 24,
  "rotate": 0,
  "price": 700,
  "price_original": 700
}
```

Следующее место 5055 имеет номер `12` и `x=210`: нумерация в этом участке
идёт против увеличения координаты X. ID, номер и физический порядок различаются.
Цены отображаются сайтом в рублях; внутри бота переводить в копейки через Decimal.
`series` → метка ряда, `place` → метка места, `block` → название сектора;
эти метки не превращать в универсальные числовые индексы.

Для s3159 ответ схемы содержал 362 места с базовым `free`, а отдельный ответ
занятости — 288 записей `sell`, например `"5289": {"status": "sell"}`.
**Нельзя выбирать места только по `hall/hall.status`.** JS накладывает карту
занятости на схему; отсутствие записи в успешно полученной полной карте снимает
занятость, сохраняя `disabled` для отключённых мест. При ошибке/неполном ответе
отсутствие записи не означает свободное место. Новые неизвестные статусы считаем
недоступными. Эти два чтения не образуют атомарного снимка: перед заказом нужна
повторная проверка и обработка конфликта на стороне продавца.

## Ограничения, наблюдённые на s3159

`event_id=386`, `hall_id=16`; ID в данных встречаются и числами, и строками.

| Поле | Значение при исследовании | Последствие |
| --- | --- | --- |
| `sell.available` / `sell.max` | `true` / `4` | Обычная покупка до 4 мест на этом сеансе |
| `book.available` / `book.max` | `false` / `0` | Отдельная операция бронирования здесь отключена |
| `collectiveSell.available`, `min`, `max` | `true`, `2`, `5` | Другой сценарий, не использовать как автоматический обход `sell.max` |

Это снимок одного сеанса, не постоянные лимиты театра. Проверять их при каждом
оформлении. Временное удержание в процессе `sell` и отдельное действие `book`
имеют разную семантику; отключённый `book` не доказывает отсутствие удержания
при покупке, но и не подтверждает его.

## Начало оформления: подтверждено только чтением кода

1. Приложение зала отправляет родителю `action` и `selectedItemsInfo`.
   Для обычного сеанса структура выбора:

   ```text
   sessionAnyplaces:
     hallplaces: [provider_place_id, ...]
     entranceplaces: {}
     count: N
     amount: сумма в единицах сайта
   ```

2. Страница выполняет jQuery `POST https://quicktickets.ru/ordering/initAnytickets`.
   К структуре выбора добавляются `organisationAlias`, `elemType=session`,
   `elemId`, `collectiveSell=0`. В коде используется сериализация формы jQuery,
   не JSON; точное кодирование вложенных массивов закрепить сетевой записью.
   Read-only проверка `jQuery.param` на текущей странице 26.09.2026 подтвердила
   имя повторяемого поля `sessionAnyplaces[hallplaces][]`. Первая live-попытка
   адаптера использовала вместо него `...[0]` и получила неоднозначный результат
   до подтверждения `hold_created`; это возможная, но не доказанная причина
   отказа. Код приведён к наблюдаемому имени поля и заголовку AJAX-запроса
   `X-Requested-With: XMLHttpRequest`; результат нового POST ещё не проверен.
3. При `res.result == "success"` страница читает `res.data.anyticketsCodes`
   и `res.data.selectAnyplacesCount`. Форма отправляет
   `POST https://quicktickets.ru/ordering/anytickets` с этими данными,
   `organisationAlias`, `elemType`, `elemId`; codes соединяются запятой.
4. Последующие поля покупателя, итоговые POST, редиректы и URL оплаты ещё не
   исследованы. Эти два пути не называем API подтверждённой брони или оплаты.

## Предварительный контролируемый checkout 17.09.2026

Выполнена одна минимальная тестовая цепочка на свободном месте публичного сеанса.
Оплата не выполнялась, персональные данные покупателя в артефакты исследования
не сохранялись. Целью было установить момент возникновения удержания и форму,
следующую за выбором места.

- `POST /ordering/initAnytickets` с одним местом вернул `result=success`.
- Последующий `POST /ordering/anytickets` открыл одну форму `POST /ordering/confirm`.
- По уточнению пользователя перед оплатой обязательны фамилия, имя, отчество,
  email, номер телефона и consent. Наблюдённая форма содержала `email`,
  `lastname`, `phone`, скрытые `paymentTerminalSystem`, `paymentTerminalType`,
  `organisationAlias`, `sessionId`, `anyticketsCodes`, `orderCode` и checkbox
  `personalDataConsent`; точные имена полей имени/отчества нужно брать из
  актуальной формы, не подставляя их по догадке.
- В отдельной карте занятости выбранное место получило статус `short_lock`.
  Последующий сценарий, остановленный на HTTP 302 от `/ordering/anytickets`,
  показал этот статус сразу после успешного `initAnytickets`. Следовательно,
  именно `initAnytickets` уже создаёт удержание; этот POST нельзя считать
  подготовительным или безопасно повторяемым.

Несколько последующих read-only запросов показали `short_lock`, после чего
QuickTickets начал завершать TLS-соединения до ответа. Поэтому фактический TTL,
его точка отсчёта, финальный `/ordering/confirm`, URL оплаты и статус старого
заказа не подтверждены. Новый тестовый checkout не запускался: нельзя создавать
второе удержание, пока исход первого не разрешён. Статус `short_lock` не следует
считать ни `expired`, ни `paid`.

При повторе после снятия первого lock `POST /ordering/confirm` с обязательными
контактными полями и consent вернул HTTP 200 без redirect. Выбранное место снова
получило `short_lock`, как минимум через минуту после confirm. Тело ответа не
сохранилось, поэтому не установлено, была ли показана промежуточная страница
выбора платёжной системы или ошибка валидации. Новый hold не создавать, пока этот
не перейдёт в подтверждённый терминальный статус; следующий тест должен разбирать
ответ confirm в той же cookie-сессии и выводить только очищенную структуру формы.

Позднее контролируемое воспроизведение выполнило `initAnytickets` в одной
временной cookie-сессии, после чего `/ordering/anytickets` ответил HTTP 302.
Переход намеренно не выполнялся, а заголовок `Location` в этом запуске не был
сохранён. Публичная карта после запроса показала `short_lock`. Этот результат
подтверждает момент удержания, но не раскрывает маршрут редиректа, ID заказа,
срок, сумму с комиссией или переносимую ссылку. Пока lock не получит
подтверждённый терминальный исход, следующий POST оформления запрещён.

Последняя контролируемая цепочка уточнила обязательный параметр второго POST:
`initAnytickets` возвращает не только `anyticketsCodes`, но и
`selectAnyplacesCount`; оба значения нужно передать в `/ordering/anytickets`.
Без второго параметра сервер вернул на страницу сеанса, сохранив `short_lock`.
С обоими параметрами `/ordering/anytickets` вернул форму `POST
/ordering/confirm`; в ней снова подтверждены поля контакта, consent, codes и
orderCode. После передачи контакта и consent `confirm` вернул пустой HTTP 200
без `Location`, формы или текста. Публичная карта по-прежнему показывала
`short_lock`. Поэтому HTTP-цепочка подтверждает удержание, но не подтверждает
заказ, итоговую сумму, ссылку или её переносимость.

Контролируемые повторы 19.09.2026 с валидированным приватным профилем покупателя
подтвердили этот результат. Фактическая форма содержала только видимые поля
`email` (required), `lastname` (required), `phone` и
`personalDataConsent`, а также скрытые `paymentTerminalSystem`,
`paymentTerminalType`, `organisationAlias`, `sessionId`, `anyticketsCodes` и
`orderCode`; отдельных полей имени и отчества в DOM не было. После заполнения
всех видимых полей и установки consent сервер дважды ответил `200 text/html`
с телом ровно 0 байт и без `Location`; маршрут браузера остался
`/ordering/confirm`, признаков `/payment/order/<opaque-order-token>` не было.
В этих повторах использовался `requestSubmit()` без конкретной submit-кнопки.
Следующая проверка должна воспроизвести обычный клик по фактическому submitter:
его `name`/`value` или `formaction` могут быть частью контракта. До проверки это
остаётся гипотезой, а пустой HTTP 200 — неоднозначным результатом, не успешным
заказом.

Проверка 19.09.2026 после освобождения lock обнаружила внутри формы два элемента
`button[type=submit]`. У обоих отсутствовали `name` и непустой `value`; значение
DOM-свойства `formAction` совпадало с action родительской формы. Confirm не
отправлялся, потому что выбор одного из двух submitter без проверки видимости,
подписи и click-обработчика был бы догадкой. Следующий запуск должен записать
только эти безопасные признаки и нажать кнопку автоматически лишь тогда, когда
видимая и доступная кнопка ровно одна. Возможное изменение скрытых полей
платёжного терминала обработчиком клика пока остаётся гипотезой.

Удержание из сценария с неполным вторым POST сохранялось более шести минут и
позднее освободилось. Точное время начала того запуска не было записано, поэтому
это не измерение TTL. Он опроверг раннюю рабочую гипотезу о трёх минутах; срок
оплаты в 1200 секунд задан пользователем и отражён в предоставленном HAR. После последнего `confirm` QuickTickets несколько
раз подряд оборвал TLS до ответа и для Python, и для curl. Терминальный исход
этого hold пока не подтверждён. Новый изменяющий POST запрещён до успешного
reconciliation; следующий контролируемый запуск нужен в полноценном браузере
с сохранением network trace (после устранения TLS-блокера) и сериализацией всех
успешных значений `select`/checkbox полей формы.

Проверка headless Chrome в текущей среде тоже завершилась TLS ошибкой
`net_error -100` при загрузке публичной страницы сеанса. Следовательно, это не
различие HTTP-клиента и браузера, а внешний сетевой блокер данного исследования.
Для закрытия шага нужен запуск сохранённого browser trace из среды, где страница
QuickTickets открывается стабильно; результатом должны стать обезличенные данные
о финальном ответе confirm, URL оплаты и последующем состоянии заказа.

## Страница оплаты в предоставленном HAR

Пользователь предоставил приватный HAR, который исключён из Git правилом
`*.har`. Его содержимое не копируется в документацию: в нём есть cookies,
идентификатор заказа, QR-код и платёжные URL. Из него подтверждены следующие
обезличенные факты:

- После checkout существует `GET /payment/order/<opaque-order-token>` на
  `quicktickets.ru`, ответ — HTML-страница «Quick Tickets, оплата заказа».
- Страница показывает таймер оплаты и кнопку перехода к оплате; срок, сообщённый
  пользователем, — 20 минут (`1200` секунд). Этот срок является настройкой
  `expected_hold_ttl_seconds` и интервалом следующего RenewalCycle.
- Проверка исхода выполняется через `GET /payment/check_payment` с параметром
  `orderCode`; JSON имеет поля `result` и `message`.
- Пользователь подтвердил, что страница оплаты открывается в другом браузере.
  Ссылка признаётся переносимой, хранится только в закрытых эксплуатационных
  данных заказа и передаётся Telegram как URL кнопки по ссылке из outbox.
  Её значение не попадает в текст сообщения, batch payload, логи, Git или preview.

Для live checkout профиль покупателя обязан содержать фамилию, имя, отчество,
email, номер телефона и согласие. Значения профиля, orderCode, cookies и полный
URL страницы оплаты — секреты эксплуатации. `/payment/check_payment` известен,
но не вызывается автоматически: пользователь выбрал повторное оформление каждые
1200 секунд до `/stop` без проверки оплаты.

## Нормализованный контракт адаптера

Реализация шага 13 отделяет потенциально изменяющий browser/HTTP transport от
проверки результата. До первого write сохраняется стадия `write_started`; сам
transport обязан фиксировать последующие удалённые стадии через переданный
recorder. `dry_run` возвращается до вызова transport. Timeout после этой границы
даёт только `ambiguous` и не повторяет POST.

Наблюдение transport признаётся подтверждённым заказом только при одновременном
совпадении точного упорядоченного списка provider seat ID, полной суммы и валюты,
наличии provider order ID, aware `held_at`/`expires_at` с положительным окном и
переносимой HTTPS-ссылки вида
`https://quicktickets.ru/payment/order/<opaque-token>`. Полный URL и buyer context
скрыты из `repr`; страница сеанса, другой host, HTTP, fragment или отсутствие
подтверждения переносимости дают типизированный неоднозначный результат. Sold,
истёкшая авторизация и CAPTCHA остаются отдельными исходами. Это проверка
handoff, а не проверка оплаты: `/payment/check_payment` адаптер не вызывает.

## Reconciliation изменяющего checkout

Startup recovery различает сбой до первого write и сбой после зафиксированной
стадии `write_started`. До write тот же intent можно продолжить без внешнего
lookup. После write автоматический повтор запрещён до результата
`found/not_found`: `found` заново проходит проверку полного заказа,
`not_found` разрешает технический retry того же цикла, а `unknown`, timeout или
`unsupported` переводят Candidate в `needs_attention` с активным allocation.

Подтверждённого публичного QuickTickets endpoint для поиска результата
изменяющего checkout пока нет, поэтому production reconciliation transport
возвращает `unsupported`, а не имитирует отсутствие заказа. Известный по HAR
`/payment/check_payment` не используется для recovery: это проверка оплаты, от
которой пользователь отказался в автоматическом цикле. Отмена также не
вызывается.

## Что обязательно выяснить до включения live

- Где именно возникают заказ и удержание, его ID и подтверждённый состав;
  как отсчитываются сообщённые пользователем 1200 секунд, есть ли `held_at`,
  `expires_at` или остаток TTL и чем фактический срок может отличаться.
- Обязательные данные покупателя, авторизация, cookies, CSRF и условия форм.
- Полная сумма с комиссиями; возможен ли отказ от неподходящей суммы до удержания.
- Атомарность заказа на N мест, ответы на занятое место и частичное оформление.
- Как восстановить заказ после таймаута; есть ли поиск своего заказа, статус,
  отмена и поддерживаемый механизм идемпотентности. Не придумывать endpoints.
- Как получить URL оплаты/заказа, открываемый из Telegram на другом устройстве
  без cookie jar бота; проверить в чистом браузерном контексте.
- Как отличить paid, expired и cancelled — это не требуется для автоматических
  циклов текущей версии: пользователь выбрал явную остановку вместо status-check.
- Какая серверная семантика у наблюдённого `short_lock`, какие данные и момент
  переводят его в следующий статус, как получить его состояние без cookie и
  как подтвердить снятие удержания после ошибки транспорта.
- Различать истечение удержания и окончательное закрытие заказа для оплаты —
  будущая операционная возможность, не блокирующая продуктовый таймер 1200 секунд.

Исследовательский шаг: записать минимальный сценарий оформления в браузере
с сетевой трассировкой до оплаты, очистить секреты из примеров, затем проверить
восстановление и переносимость URL. Повтор HTTP-сценария допускается только
после понимания последствий каждого запроса. При необходимости использовать
Playwright в отдельном адаптере; он сам по себе не решает переносимость ссылки.

Если удержание или переносимая ссылка недоступны, зафиксировать ограничение и
временно выдавать уведомление/подбор со ссылкой сеанса. Такой режим полезен,
но **не завершает** требование автоматического оформления; оно остаётся открытым.
