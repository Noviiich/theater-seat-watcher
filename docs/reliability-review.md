# Проверка скорости и устойчивости — 26.09.2026

Проверен локальный код приложения: обнаружение новых сеансов, строгий подбор
соседних мест, оформление через fake provider, SQLite и доставка через fake
Telegram. Проверка выполнялась как дополнение шага 18 roadmap. Изменения не
развёрнуты на сервере; реальное создание заказа и отправка в Telegram в этой
проверке не выполнялись.

## Исправления

- После сохранения каждого подтверждённого заказа отправка просыпается сразу.
  Медленный следующий checkout не задерживает уже готовую ссылку.
- Сохранённый intent, до внешнего запроса которого процесс упал, возобновляется
  в live runtime с тем же идентификатором. Ранее resume worker существовал,
  но не был подключён к production. Явная остановка, пауза, изменение версии
  подписки и истечение срока не разрешают такое оформление.
- Ошибка сохранения подтверждения Telegram больше не оставляет сообщение
  в `sending` до рестарта: следующий проход восстанавливает claims.
- TTL проверяется перед каждой отправкой с актуальным временем. Истёкшую
  в процессе обработки пакета ссылку не отправляем. Новая ссылка доставляется
  до необязательного редактирования предыдущего сообщения.
- Блокировка единственного runtime продлевается во время восстановления и
  ожидания текущих задач при shutdown. Потеря блокировки останавливает работу.
- Сигнал о новых задачах не обходит backoff. Runtime уважает полный
  `retry_after`; более тысячи последовательных ошибок не переполняют экспоненту.

## Проверки

Добавлены регрессионные тесты доставки первого заказа при заблокированном втором,
восстановления после сбоя записи подтверждения отправки, истечения ссылки перед
отправкой, защиты resume остановкой/паузой/сроками/версией подписки, долгой серии
ошибок, сохранения lease при recovery и shutdown, потери lease при recovery.
Существующий тест восстановления intent проверяет теперь полный workflow.
Общие тесты также проверяют соседство, лимиты, дедупликацию, несколько сеансов,
повторные циклы и неоднозначные ответы оформления.

Итог: `pytest` — 172 passed, 1 skipped (явно включаемый live E2E).
`ruff check`, `ruff format --check`, `mypy src`, проверка diff и локальных
ссылок изменённой документации прошли.

Выполнено чтение публичного QuickTickets штатным read-only клиентом:

| Наблюдение | Результат |
| --- | --- |
| Полный снимок афиши | 26 сеансов, 14,767 с |
| Повторное чтение с сохранёнными деталями | 0,407 с, тот же fingerprint |

Это единичные измерения из текущего окружения, а не SLA. Запросов создания
удержаний и проверки оплаты не было. Профиль покупателя, токены и ссылки оплаты
в протокол не включаются.

## Границы результата

Период афиши по умолчанию — 2,5 секунды между началами проходов. К задержке
обнаружения добавляются загрузка деталей нового сеанса, проверка наличия,
checkout и доставка. Первый снимок после запуска без сохранённых деталей
дольше обычного. Оформления одного покупателя выполняются последовательно.

Наличие свободных мест само по себе не гарантирует платёжную ссылку: нужна
непрерывная группа заданного размера, допустимая цена с комиссией, подходящий
профиль зала, открытая продажа и успешный checkout. Места могут занять между
чтением и оформлением. При отсутствии группы повторная проверка по действующим
настройкам выполняется через 180 секунд, при успешной брони новый цикл — через
1200 секунд. Уже известные сеансы baseline автоматически не оформляются.

Неизвестный исход изменяющего запроса нельзя повторять вслепую. Автоматический
lookup QuickTickets пока не подтверждён; такие случаи требуют внимания
оператора. Долгая недоступность Telegram может пережить срок ссылки; отправка
истёкшей ссылки не считается успехом. Следующий разрешённый цикл создаёт новую
бронь. Для полной live-приёмки нужны фактическая соседняя группа, переносимая
ссылка на оплату и один повтор через 1200 секунд по шагу 20 roadmap.
